## Добавленное покрытие

1. 11 GET-сценариев без X-API-KEY: запрос содержит валидные обязательные
   параметры, чтобы проверка авторизации не подменялась проверкой валидации.
   Проверяются отказ, JSON, сообщение ошибки и отсутствие данных в ответе.
   При отсутствии точного контракта допускаются 401/403; для поиска клиента
   другой клиники допускается также 404. Точные статусы требуют согласования.
2. Соответствие телефона заранее известному ID клиента основной клиники.
3. Пустые admissions, recomendations, vaccinations, discountCard для
   существующего клиента без данных. Перед проверкой выполняется positive
   control: телефон разрешается в ожидаемый ID.
4. Изоляция телефона другой клиники: под ключом владельца находится ожидаемый
   клиент, под ключом основной клиники доступ отклоняется и данные не выдаются.

Изоляция по чужому client_id пока не добавлена: без подтверждения глобальной
уникальности ID такая проверка может обратиться к другому локальному клиенту
основной клиники и дать ложный FAIL.

Итого добавлено 17 сценариев: 11 без ключа и 6 с контролируемыми данными.

## Данные для шести сценариев

Пользователь предоставил тестового клиента для отдельной проверки
соответствия телефона ID; она прошла на production. Подтверждённый клиент
сохранён в игнорируемом test-artifacts/qa-client-data.json без ФИО и ключей.
Существующая пара CLIENT_PHONE/CLIENT_ID в .env не изменялась.

Fixture читает внешний JSON из --qa-client-data или PIV_QA_DATA_FILE.
Runner передаёт путь через --qa-data, без изменения environment variables.
Пустой объект `{}` допустим
как незаполненный файл: зависимые сценарии явно SKIP. Неверные заполненные
данные приводят к FAIL, а не к скрытому пропуску. Сам файл в репозиторий
добавлять не требуется; ключи и пароли в нём не нужны.

| Секция | Поля |
|---|---|
| primary_client | id: positive integer, phone: string, clinic_code: код основной клиники |
| empty_client | id, phone, clinic_code основной клиники, confirmed_empty: true |
| foreign_client | id, phone, clinic_code другой клиники, phone_absent_in_primary_clinic: true |

Пустой клиент должен существовать в основной клинике и не иметь данных
во всех четырёх проверяемых коллекциях. Телефон foreign_client должен
отсутствовать в основной клинике. При отсутствии доступа к clinic key
владельца positive control завершится FAIL; такой результат не доказывает
нарушение изоляции.

## Выдача API key без авторизации

**Классификация:** UNKNOWN — ожидаемый режим доступа требует уточнения.
Пользователь подтвердил, что требование нужно уточнить. FAIL этого сценария
пока не является доказательством PRODUCT BUG и не обосновывает NO-GO.

**Шаг:** GET /apiKey/byClinicCode с действующим code основной клиники,
Accept: application/json, без X-API-KEY, Authorization и cookies.

**Фактически:** HTTP 200, JSON, success=true, непустой data.apiKey.
Наличие непустого ключа подтверждено диагностикой без сохранения значения.
Тест на отказ в доступе остался FAIL; ожидание не подогнано под ответ.

**Ожидалось в добавленной проверке:** закрытый endpoint отклоняет запрос
без ключа с 401/403 и не выдаёт API key. Применимость этого ожидания
именно к /apiKey/byClinicCode пока не подтверждена.

**Решение:** уточнить, должен ли endpoint быть публичным bootstrap endpoint.
Если да — заменить ожидание этого сценария проверкой публичного получения
ключа. Если нет — оформить PRODUCT BUG и исправить контроль доступа backend.

## Запуск

```powershell
.\.venv\Scripts\python.exe -m pytest qa_checks -q -o addopts=''
.\.venv\Scripts\python.exe -m pytest tests --collect-only -q -o addopts=''
.\.venv\Scripts\python.exe -m qa_checks.run_readonly_api --priority
.\.venv\Scripts\python.exe -m qa_checks.run_readonly_api --priority --case client-data --qa-data test-artifacts/qa-client-data.json
```

Обычный pytest использует прежний bootstrap проекта. Для текущего
production-прогона без изменения .env используйте изолированный runner.
