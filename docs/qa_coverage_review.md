## Что усилено

- Существующие строгие проверки типов и обязательных полей Pydantic сохранены.
- Positive: JSON Content-Type, валидный JSON, success=true для PIV envelope.
- Token: status=200, непустые token/user_id; apiKey/domain — непустые строки.
- Client ID и телефонный префикс должны быть положительными.
- Коллекции: totalCount неотрицательный и не меньше количества возвращённых
  элементов. Равенство намеренно не требуется: семантика totalCount и
  пагинация этих endpoints не подтверждены. Для vaccinations считаются
  внешние группы; точный контракт количества требует уточнения.
- Статьи: не больше трёх lastThree, уникальность id внутри результата;
  запрошенные page/size, диапазон from/to, число элементов и крайние ссылки.
- Negative: success=false, непустые сообщения, совпадение status с HTTP
  для token; непустой errors и сообщения по обязательным полям для 422.
- Проверки missing parameter поддерживают объект и singleton list.
- Тест отсутствующего app_name использует credentials из конфигурации.
- Positive clientByPhone использует существующую настройку CLIENT_PHONE.

Проверки пагинации основаны на стандартной семантике полей существующей
схемы. Значения status в token, положительные идентификаторы и смысл success
следуют из действующих сценариев авторизации и успешных операций.
Проверки GET endpoints выполнены на текущем URL. Для /articles схема
прошла, но проверки пагинации остановились на некорректном Content-Type.
Проверки token/SMS/event в этом прогоне не выполнялись. Дополнительные
business expectations необходимо сверять с требованиями; будущий FAIL
сам по себе не доказывает дефект продукта.

## Подтверждённые риски тестового проекта

1. **Высокий:** .env отслеживается Git; bootstrap записывает туда ключи.
   Credentials, X-API-KEY и ответ token не маскируются в cURL/Allure;
   failure_report также сохраняет их в JSON, доступный уведомлениям.
   Рекомендация: исключить секреты из version control, оценить необходимость
   ротации и маскировать данные до записи артефактов. В рамках этой работы
   .env, секреты, CI и инфраструктура отчётов не изменялись.
2. **Высокий:** default URL — production; полный запуск отправляет SMS и
   записывает событие. Для таких сценариев нужен выделенный тестовый dataset.
3. **Средний:** autouse bootstrap делает даже независимые negative tests
   зависимыми от успешной авторизации и доступности обоих сервисов.
4. **Средний:** фиксированные client_id/телефоны в части тестов; валидность
   dataset и соответствие клинике не подтверждаются.
5. **Средний:** 500 при проверке SMS считается ожидаемым результатом.
   Без актуального контракта нельзя ни объявить это PRODUCT BUG,
   ни считать достаточным отрицательным сценарием.
6. **Средний:** extra=allow допускает новые поля, media/vaccine_description
   описаны частично; ошибочное содержимое этих вложенных объектов может пройти.

## Приоритет дальнейшего покрытия

P1: отсутствие авторизации, изоляция данных между клиентами/клиниками,
соответствие ответов контролируемым fixtures, positive SMS check на стенде.
P2: пустые/неверные типы/границы параметров; точные business errorCode;
вложенные media, сортировка статей и семантика totalCount.
Новые статусы и business assertions добавлять после сверки с OpenAPI
или подтверждёнными требованиями, не по фактически полученному ответу.

## Обнаруженное несоответствие /articles

**Классификация:** PRODUCT BUG — Content-Type не соответствует JSON-телу.
Причина на уровне продуктового кода не установлена.

**Окружение:** https://petinvet.ru/api/v2, 13 октября 2026.

**Предусловия:** clinic API key, полученный GET /apiKey/byClinicCode;
заголовки Accept: application/json и X-API-KEY.

**Шаги:** выполнить GET /articles с page=1,size=10; повторить с
page=1,size=1 и page=2,size=1.

**Ожидалось:** HTTP 200, JSON Content-Type, тело по GetArticlesResponse.

**Фактически:** во всех трёх вариантах HTTP 200,
Content-Type: text/html; charset=UTF-8. Тело декодируется как JSON и
проходит существующую строгую GetArticlesResponse; новая проверка
Content-Type падает. Семантические assertions пагинации после неё
не выполнялись, поэтому их live PASS не заявляется.

**Доказательства:** test-artifacts/readonly-results.json содержит
nodeid, HTTP-статус, путь, Content-Type и причину FAIL без секретов.
Предыдущий сетевой прогон сохранён в
test-artifacts/readonly-existing-key-results.json.

**Решение:** проверить формирование JSON-response и заголовков на backend
и proxy для /articles. Продуктовый код в этом репозитории отсутствует.

**Нужно ли менять автотест:** нет, проверка Content-Type сохранена.
