# Расхождения реальных ответов PIV со Swagger

**Дата:** 13 октября 2026.
**Проверенное окружение:** https://petinvet.ru/api/v2.
**Документ:** предоставленный swagger.yaml, OpenAPI 3.0.0, info.version 3.0.
В servers.url документа указан https://petinvet.online/api/v2.
Нужно подтвердить актуальность документа для .ru; ниже перечислены
подтверждённые различия ответов .ru и предоставленного контракта,
без автоматического отнесения всех различий к багам backend.

## 1. Получение API key без авторизации

**Запрос:** GET /apiKey/byClinicCode?code=<действующий код домена>,
Accept: application/json, без X-API-KEY/Authorization/cookies.

**Swagger:** security: ApiKeyAuth; заголовок X-API-KEY обязателен
(paths./apiKey/byClinicCode.get.security, строки 725–726).

**Фактически:** HTTP 200, success=true, непустой data.apiKey.
Значение ключа не включено в отчёт.

**Уточнение:** endpoint действительно должен быть публичным bootstrap
endpoint или проверка авторизации отсутствует? Если публичным — исправить
security и общее описание защищённых роутов в Swagger.

## 2. Ошибки возвращаются массивом вместо объекта

**Swagger:** корневой type: object.
**Фактически:** корневой JSON array из одного объекта ошибки.
Схематично: документация `{success, message, data}`, API
`[{success, message, data}]`. Названия полей здесь обозначают структуру,
а не дословный JSON/значения ответа.

Подтверждено для следующих комбинаций endpoint/status:

| Метод и endpoint | HTTP-статусы с расхождением |
|---|---|
| GET /apiKey/byClinicCode | 400, 404 |
| GET /clients/clientByPhone | 400, 403, 404 |
| GET /getPhonePrefix | 403 |
| GET /domainName | 403 |
| GET /admissions | 400, 403 |
| GET /medicalCards/recomendations | 400, 403 |
| GET /medicalCards/vaccinations | 400, 403 |
| GET /clinics | 403 |
| GET /articles/lastThree | 403 |
| GET /articles | 403 |
| GET /discountCard | 400, 403 |
| POST /event | 400, 403 |
| POST /sms/send | 400, 403 |

**Воспроизведение:** 400 — не передавать обязательный code/phone/client_id;
для /event отправить `{}` либо `{"device_id":1}`; для /sms/send — `{}`.
403 — передать невалидный X-API-KEY при остальных валидных параметрах.
404 — code=99999999 или phone=0000000000 в соответствующих GET endpoints.

GET /articles с отсутствующими page/size возвращает 422 объектом;
его в эту группу расхождений не включаем.

**Источник:** response schemas конкретных операций и
components.schemas.ErrorResponse403/ErrorResponse404, строки 105/122.

## 3. Скидочные карты: форма data

**Запрос:** GET /discountCard?client_id=1414, действующий ключ домена.
Также наблюдалось для пустого клиента 1640.

**Swagger:** DiscountCardsResponse.data — array групп
`[{totalCount, card:[...]}]`, строки 601–611.
**Фактически:** data — object `{totalCount, card:[...]}`.

**Уточнение:** определить одну актуальную форму ответа либо описать
обоснованные варианты схемой oneOf. Сейчас объект в Swagger не описан.

## 4. Скидочные карты: тип number

**Запрос:** GET /discountCard?client_id=1414 после добавления карты.
**Swagger:** DiscountCardItem.number — integer, строки 582–583.
**Фактически:** string, состоящая из цифр.

**Уточнение:** если номер карты — строковый идентификатор, закрепить string
в контракте; если API обязуется возвращать integer, исправить сериализацию.
Значения номеров в отчёт не включены.

## 5. Скидочные карты: тип is_default

**Swagger:** DiscountCardItem.is_default — boolean, строки 588–589.
**Фактически:** integer 0/1.

**Уточнение:** согласовать boolean true/false или integer с enum [0,1]
и привести документацию/API к одному представлению.

## 6. Скидочные карты: nullable start_date и end_date

**Swagger:** оба поля type: string, nullable не указан, строки 590–593.
**Фактически:** оба поля присутствуют со значением null у карты без дат.

Пользователь подтвердил создание карты без срока действия в ВМ и
предоставил скриншот. Бизнес-сценарий допустим; в Swagger нужно описать
его представление, например string + nullable: true. Наличие поля и
nullable значение — разные требования: required у DiscountCardItem
вообще не указан.

## 7. Вакцинации: дополнительный уровень массива

**Запрос:** GET /medicalCards/vaccinations?client_id=1414.
**Swagger:** data.vaccination — array объектов VaccinationItem,
строки 404–407: `[{...}, {...}]`.
**Фактически:** array массивов объектов: `[[{...}], [{...}]]`.

**Уточнение:** описать группировку и её смысл либо вернуть плоский список.
Поля элементов внутри групп дополнительно сверены с VaccinationItem;
новых типовых расхождений для наблюдаемых записей не обнаружено.

## 8. Статьи: неверный Content-Type успешного ответа

**Запросы:** GET /articles?page=1&size=10, page=1&size=1,
page=2&size=1. Accept: application/json, действующий ключ.

**Swagger:** HTTP 200, content: application/json
(paths./articles.get.responses.200, строки 1197–1202).
**Фактически:** HTTP 200, JSON-тело, но
Content-Type: text/html; charset=UTF-8 во всех трёх вариантах.

**Уточнение:** исправить Content-Type backend/proxy для JSON-ответа.

## 9. Статьи: from и to имеют другой тип

**Swagger:** ArticlesPaginatedResponse.from и to — string,
строки 505–506 и 530–531.
**Фактически:** integer для проверенных непустых страниц.

**Уточнение:** закрепить числовые границы страницы в схеме либо подтвердить
необходимость строк. Возможность null у пустых страниц требует отдельного
контракта; на текущих страницах null для этих двух полей не наблюдался.

## 10. Статьи: nullable ссылки не описаны типами

**Swagger:** next_page_url, prev_page_url, links[].url — string,
nullable не указан (строки 516–517, 522–523, 528–529).
**Фактически:** null для ссылок на отсутствующие соседние страницы.
Наблюдалось на проверенных первых/последней страницах.

В примере самого Swagger эти поля тоже имеют null. Это внутреннее
противоречие примера и схемы, которое дополнительно воспроизводится
реальным ответом. Нужно добавить nullable: true к соответствующим свойствам.

## 11. Документированный POST /getToken возвращает 404

**Запрос 1:** POST /getToken, Content-Type: application/json,
login/password/app_name из конфигурации проекта, действующий ключ домена.
**Запрос 2:** тот же endpoint без app_name.

**Swagger:** 200 для успешной авторизации; 401 для неверных/отсутствующих
credentials и отсутствующего app_name, строки 1320–1378.
**Фактически:** оба запроса вернули HTTP 404 и JSON object.
404 для этой операции в Swagger не описан.

**Уточнение:** /getToken должен существовать на этом PIV API либо
документация должна описывать отдельную авторизацию ВМ /token_auth.php?
Заранее выполненная авторизация ВМ не подтверждает работу отдельного
документированного endpoint /getToken.

## Что фактически проверено и что не заявляется

- GET-набор: 59 API-сценариев, 48 PASS / 6 FAIL / 5 SKIP по текущим
  тестовым assertions. Эти числа не означают, что 48 ответов полностью
  соответствуют Swagger: тесты уже допускают отдельные варианты схем.
- Дополнительно отдельно проверены успешный /clinics и вложенные элементы
  вакцинаций. /clinics сейчас вернул data.clinics и totalCount — его
  успешная форма не включена в расхождения.
- POST: 9 запросов; позитивные /event и /sms/send дали 200, JSON object,
  success=true без найденных расхождений описанных типов.
  Доставка SMS и сохранение события отдельно не проверялись.
- /sms/check, неизвестные негативные значения/границы и другие неподготовленные
  комбинации в этом аудите не запускались. Расхождения для них не заявляются.
- Сравнивались типы, структура присутствующих полей, media type,
  документированные HTTP-статусы и требование API key. Примеры Swagger
  не использовались как точные ожидаемые значения IDs/текстов/дат.
  Форматы, бизнес-полнота записей и все возможные состояния не проверены.
- .env не изменён; credentials, реальные ключи, номера карт и тела
  ответов в файлы отчётов не включены. Выполнен один позитивный POST
  /event с QA-заголовком и один позитивный /sms/send на номер клиента 1640.
